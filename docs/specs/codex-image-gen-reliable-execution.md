# Codex Image Gen：继承上游能力、可靠恢复与有限自动重试

Status: ready-for-agent

本规格来自已完成的设计讨论；不是重新征求产品决策。目标仓库为 CWen001/pi-everyday，GitHub Issues 为本项目已有的 issue tracker。

## Problem Statement

用户希望通过自己的 Codex 高级订阅生成或编辑图片。现有技能把“生成了图片”“执行记录可以完整识别”“允许交付图片”捆绑成一个结果。即使图片已经完成，日志格式变化、合法异步等待或不同的调用写法也可能使任务被报告为失败，需要用户和外层 Agent 手工找回图片。

现有实现还额外限制单张参考图，拒绝自动重试，并在成功转存后删除源图片。这些限制不再符合用户需求：继承 Codex 上游原生能力；失败时自动处理；若恢复或重试产生多张有效图片，全部展示并说明情况，而不是替用户选择或隐藏。

维护目标是尽量跟随最新上游最佳实践，不是冻结在当前安装版本；同时不需要每次生图都强制升级 Codex。已有代码和安装副本存在未提交修改，实施不得覆盖无关工作，也不能把安装副本当作唯一源码。

## Solution

保留一个小的 Image Execution CLI interface：创作提示词、上游支持的参考图片，以及可选输出位置。其 implementation 负责 Codex 执行、原任务等待、结果恢复、有限重试、Artifact Custody 和如实报告。

一个 Image Request 可以包含多个 Image Runs，最多允许三次实际生成尝试。恢复已有结果优先于重新生成；等待同一个任务、修复本地问题和重试保存不消耗生成尝试。已有有效结果时，不因审计兼容性问题再次生成。

图片结果与执行检查结果分别表达。未知日志格式不等于生图失败，也不等于已经通过检查。所有来源明确且有效的图片都保留、展示，并关联到各自 Image Run。艺术质量与取舍由用户决定。

## User Stories

1. 作为用户，我希望通过 Codex 订阅与内置 image_gen 完成生成，而不是被悄悄切换到付费 Images API 或其他供应商。
2. 作为用户，我希望现有的 stdin 提示词、单参考图和可选输出位置用法继续可用，以免重新学习基本调用方式。
3. 作为用户，我希望创作提示词原样进入执行流程，而不是被 runner 自行补写风格、情节或审美要求。
4. 作为用户，我希望支持 Codex 上游允许的多参考图，并保留输入顺序与用途，不被 wrapper 人为缩减成一张。
5. 作为用户，我希望合法的本地读图、附件引用与异步等待遵循上游指导，不因狭窄工具规则被误判。
6. 作为用户，我希望新请求、编辑请求及透明背景等能力随上游发展得到维护，而不是被旧参数白名单永久锁住。
7. 作为用户，我希望知道本次实际运行的 Codex 版本及可以核实的能力信息，而不是把主线源码里的能力误报成本机已支持。
8. 作为用户，我希望修复和维护时优先采用最新上游最佳实践，必要时处理版本兼容，但每次出图不必强制升级或重复联网检查版本。
9. 作为用户，我希望任务仍在运行时继续等待同一个任务，而不是误报完成或提交重复生成。
10. 作为用户，我希望参考图读取等可恢复问题能被自动修复，不必每一步都重新批准。
11. 作为用户，我希望临时生成失败时自动重新尝试，每个 Image Request 最多三次实际生成，不必逐次确认。
12. 作为用户，我希望超时后先检查原任务和已有产物，避免明明有图却立即重新生成。
13. 作为用户，我希望保存或交付失败时复用已生成图片，而不是再次调用生成模型。
14. 作为用户，我希望遇到登录失效、明确拒绝或不能恢复的限流时得到清楚说明，而不是无限循环或改走其他服务。
15. 作为用户，我希望日志存在新字段、新事件或不同合法调用写法时，仍能拿到本次已完成且来源明确的图片。
16. 作为用户，我希望不完整的执行证据被标为未完全核实，而不是虚假声称“严格隔离”或“审计通过”。
17. 作为用户，我希望确实发现调用其他生成服务、修改无关项目文件等越界时停止后续自动尝试，并报告实际异常。
18. 作为用户，我希望发生越界或部分失败时，已经生成的有效图片仍然被保留并展示，不因总体异常而丢失。
19. 作为用户，我希望首次超时结果与后续重试结果都被发现时全部展示，并说明哪张来自恢复、哪张来自重试。
20. 作为用户，我希望系统不替我选美、不隐藏多余结果、不因主观审美而自动重画。
21. 作为用户，我希望原始生成文件保持完整，目标文件不被覆盖，也不把任意本地文件当成生成图片交付。
22. 作为用户，我希望正常结果简洁可读，包含全部图片和必要警告；复杂诊断留在可定位的记录中。
23. 作为维护者，我希望上游事件格式与能力变化集中在少数已有 modules 内，不泄露为每个调用者需要掌握的恢复步骤。
24. 作为维护者，我希望在不调用真实生图服务的情况下验证等待、重试、恢复和交付行为，避免每个回归测试都依赖在线生成。
25. 作为维护者，我希望源码仓库、GitHub 规格和最终安装副本保持可追踪关系，不让本地修补长期只存在于安装目录。

## Implementation Decisions

### 1. 领域与 Interface

- Image Request 是用户的一次出图任务；Image Run 是一次尝试生成的 Codex 执行。不能再用“一个请求”推导“绝不允许重试”。
- 保留 CLI 作为唯一 external seam。提示词仍经 stdin 输入，参考图扩展为有序集合，已有单参考图调用保持兼容，可选输出位置仍然支持。
- 不增加公共程序库 interface、provider 抽象、adapter 注册机制或通用工作流框架。
- 继续使用现有的执行编排、Rollout 解读和 Artifact Custody 这几个 internal seams。复用并简化已有 modules，而不是另包一层服务。
- 多图输出必须成为结构化结果的一等内容。若为旧调用保留单个 path，它只能是确定顺序的兼容别名，不能表示自动评选的最佳图或取代完整图片列表。

### 2. 上游能力与版本维护

- 执行路线仅为 Codex 订阅下的内置 image_gen。不得将 agent 模型选择参数误当成图片模型选择参数，也不得声称 runner 可以覆盖上游未开放的图片模型字段。
- 以最新上游公开行为和指南为维护依据；实际执行必须尊重实际运行版本的工具契约。不能把“兼容当前版本”固化为长期不更新，也不能假装旧版本已支持新能力。
- 移除 wrapper 自设的单参考图限制与调用代码形状限制。参考图数量及参数组合遵循上游原生限制，不另造更窄的规则。
- 遵循上游对本地图片路径、对话附件、查看图片和异步等待的指导。必要的读图与等待不是越界；同时兼顾实际存在的参考图读取故障，恢复时使用合法替代路径而不更改创作目标。
- 工具参数与能力应尽量由 Codex 原生契约负责；不自建第二套长期易失真的 image_gen 参数语法解析器。
- 维护、修复及发现不兼容时核对最新适用版本，必要时通过现有升级机制更新并记录、验证版本变化。这不是每次请求都强制更新，也不是禁止自动修复所需的版本更新。
- 新增的上游生图能力不应仅因 wrapper 的旧审计字段表而被拒绝。保留必要的输入文件可读性、路径和输出保护检查。

### 3. 创作权限

- 原样保留用户的创作提示词和明确指定的参考素材，不自动增加场景、风格、角色或构图要求。
- 允许添加与创作内容分离的执行说明，例如使用内置工具、等待完成、限制自动尝试次数。
- 不承诺内部模型绝不改写提示词；本规格约束的是 wrapper 与外层 Agent 不擅自重写创作意图。
- 不进行自动审美评价、质量排名或主观重画。技术有效性不等于用户已经接受艺术效果。

### 4. 有限自动重试与恢复

- 每个 Image Request 最多三次实际生成提交，包括首次；无需逐次向用户确认。不会因为使用高级订阅而无限循环。
- 继续等待同一个异步任务、读取本次执行记录、恢复图片、修复保存问题，不计为新的生成提交。
- 避免 Codex 内部隐式重试和外层 runner 重试叠加：实际生成次数必须可追踪，不能让每层都各自尝试三次。
- 尚未提交生成的本地故障可自动修复；无法恢复的输入错误明确返回，不空转消耗重试。
- 生成仍在运行时等待原任务；已经完成时恢复和交付；明确的临时生成错误可以退避后重新提交。
- 超时或非零退出不能单独证明没有图片。先检查原任务状态及本次调用已返回的结果；无法恢复时，允许在剩余预算内重新提交，并保留第一次可能已经生成的事实。
- 不启动竞争性并发生图。前一次状态无法确认时，对潜在重复结果明确记录；返回前再次检查已知 Image Runs 的可恢复结果。无需引入长期后台监听服务。
- 没有图但只是重复的本地保存错误时，不应通过反复生图解决。保留可恢复来源并报告真实错误。
- 登录失效、明确内容拒绝、真实越界及持续不可恢复错误不是盲目重试对象。限流若带可用恢复时间可按合理运行期限等待，否则清楚停止；不得切换其他接口绕过。
- 保留有界等待与进程生命周期管理，不允许等待或本地恢复无限循环；不要把现有单次进程超时机械叠加为不可控总时长。

### 5. 图片结果与执行检查分离

- 图片结果表达是否仍在运行、已有有效产物、没有有效产物或仅部分产物完成交付；执行检查单独表达已核实、证据不完整或已发现真实越界。
- Rollout 解读应从实际完成事件和返回产物提取证据，支持历史完成事件、Extension 完成项、返回的内联图片数据和合法异步等待。
- 相同生成任务的新旧格式完成记录应按身份去重，不因一张图出现两种事件表示而判为两次生成。
- 未知日志事件、未知附加字段或无法识别的合法包装写法，导致的是检查不完整，不自动等同于生成失败或真实越界。
- 不执行 Rollout 中的代码，也不要求一段 JavaScript 必须与某个正则模板一致才允许交付。无法从现有证据确认的行为如实标为不确定。
- 会话、调用与产物之间仍须有可信对应。不能因降低日志格式耦合而从其他会话或任意磁盘位置猜测一个结果。
- 确认发生真正越界时停止后续自动尝试，展示和保留所有已经确认有效的图片，说明发生了什么；不得通过一次新尝试掩盖异常。
- 有有效产物且仅存在检查兼容性警告，可以正常交付并显式带警告。明确越界或尚未完成交付不能被包装成普通成功；结构化结果中仍须包含已保存图片。

### 6. Artifact Custody 与多结果交付

- 保留 Codex 原始文件。交付采用不覆盖的复制，不在成功后删除源文件。
- 来源限于本次 Image Run 明确返回的图片数据或可以证实与其关联的原生生成产物。不得广泛扫描磁盘、借用其他调用图片或复制日志任意指向的文件。
- 恢复内联数据时验证其确为可解码图片；对所有产物验证技术有效性而不是仅相信扩展名。不得把 base64 数据输出到面向用户的日志或回复中。
- 保留来源验证、文件身份检查、目标独占创建及失败清理等必要安全性质，但不为删除源文件维护不再需要的事务复杂度。
- 输出位置冲突不覆盖、不删除原有文件，也不因此重新生成。保留原图并清楚说明冲突；其他结果使用可追踪、不冲突的位置。
- 每张独立的有效生成图片均列出并展示，说明所属尝试、正常完成或超时后恢复、交付位置和检查警告。去除的是同一产物的重复事件，不是替用户删掉不同尝试的图片。
- 多结果按稳定、可解释的顺序呈现，例如尝试顺序；不排名、不自动选美。
- 若宿主支持直接展示图片，逐张展示；否则逐张提供可访问路径或链接，并说明情况。
- 保存一个结果失败，不得丢弃其他已经成功保存的结果，也不得抹掉该结果的可恢复来源。

### 7. 部署与兼容

- 在连接目标 GitHub remote 的源码 checkout 中实施；保留已有未提交工作，只合并本规格所需修改。
- 先验证源码，再通过既有包安装/更新方式同步实际运行的 Pi skill。不得只修改安装副本，也不得未经比较覆盖其中尚未回归源码的修复。
- 更新技能操作说明，使调用者不再需要知道旧的手工 Rollout 恢复配方，也不再宣称“一次请求只能调用一次”或“未知事件必定失败”。
- 正常回复只展示全部图片及必要说明；详细错误、运行版本和来源记录保留在可定位诊断中。不能把执行检查描述成硬工具隔离。

## Testing Decisions

### 测试 Seam

- 主要验收经过现有 CLI external seam：输入提示词、参考图片和输出位置，观察实际启动次数、返回结果、图片文件、警告、错误与源文件保留情况。
- 复用现有 fake Codex 执行器和临时文件系统测试作为 prior art；扩展其场景行为，不引入新的公共测试 interface。
- Rollout 解读继续使用已有纯输入/输出 internal seam，Artifact Custody 继续使用已有文件交付 internal seam。它们用于密集测试外部不稳定证据和文件失败路径，不为每个 helper 单建测试层。
- 测试不得依赖某个私有函数名、正则、模块数量或特定变量写法。已有检查旧政策的测试应被替换，而不是与新政策同时保留。

### 必须覆盖的可观察行为

1. 无参考图、单参考图和原生允许的多参考图正常工作，提示词内容与参考顺序保留。
2. 合法查看参考图、附件引用和同一异步任务的多次等待不会触发新的生成或越界误报。
3. 单次成功只提交一次生成；失败后成功的请求提交两次；持续临时失败最多三次。
4. 本地预检失败、等待、恢复和保存重试均不消耗额外生成次数；不存在内外层重试相乘。
5. 图片完成后遇到保存失败，复用原图片而不再生成。
6. 进程超时或非零退出但产物已经完成时，恢复有效产物并说明执行异常。
7. 首次超时、后续成功、随后找回首次结果时，全部独立图片保留并出现在输出中。
8. 未知非关键日志事件和附加字段不阻止来源明确的有效图片交付，且检查状态明确为不完整。
9. 同一次生成同时出现两种完成事件时去重，不误报重复生成；不同生成结果不被合并隐藏。
10. 已返回内联图片数据但没有保存路径时可以恢复；无效或截断数据不会被当作有效图片。
11. 不同合法调用写法不会因变量名、参数顺序或新增原生字段被单纯正则拒绝；解析不完整时不虚报已完全核实。
12. 错误会话、无法建立调用来源、任意文件路径、越界读取或不安全目标不会被降级成普通兼容性警告后放行。
13. 确认真实越界后停止自动重试，但保留并报告已经产生的有效图片与异常。
14. 登录失效、明确拒绝和不可恢复错误不会形成三次同样的盲目调用；限流等待和总生命周期有界。
15. 原图保持不变；目标已存在时不覆盖；部分交付失败不删除其他成功结果。
16. 输出包含完整图片集合、尝试来源、必要警告；单路径兼容字段不隐藏其他图片；无 base64 泄漏。
17. 当前原生能力与最新上游指导存在差异时如实报告，并验证适用的兼容修复或升级，而非硬编码永远不升级或每次调用强制升级。
18. 已有无关 Pi Everyday 功能和现有单参考图基本调用不回归。

- 测试应使用真实有效的小型图片 fixture，而不是把普通字符串命名成 PNG 后据此宣称完成了图片有效性验证。
- 自动化回归默认使用离线 fixtures 与 fake Codex，不在常规测试套件里消耗真实生成。正式实施验收可执行一次明确标注的真实 smoke test，记录运行版本、图片路径和检查结果；不因艺术不满意自动重画。
- 完成实施前运行类型检查与仓库现有测试；不得仅凭离线测试通过就声称已经验证最新上游的真实生图行为。

## Out of Scope

- 其他图片供应商、Images API 路由、回退 CLI、多平台适配框架。
- 通过 agent 模型参数强制更换上游未开放的图片模型。
- 自动创作改写、审美评分、最佳图片选择、为了“更好看”无限生成。
- 每个请求强制下载或升级到最新版，或为简单能力维护建立大型动态 schema 系统。
- 取消必要的文件安全与来源验证，伪称硬工具隔离，或将未知证据直接视为通过。
- 无限重试、竞争性并发生图、跨会话全盘图片搜索或长期后台结果监听服务。
- 删除原图、覆盖用户文件、清理与本请求无关的 Codex 数据。
- 无关的 Path Rendering、usage-status、其他扩展修改。
- 在写入本规格时修改运行代码、触发真实生图、提交或推送代码、发布包。

## Further Notes

### 与旧规格的关系

本规格明确替代 #2 和 #4 中与 Image Execution 相关且冲突的要求，包括：禁止自动重试、仅一张参考图、未知 Rollout 格式一律失败、其他工具一律视为越界、成功交付后删除源图，以及永远只输出一个图片路径。旧规格的 Path Rendering 要求不受影响。

来源与文件安全、保持简单 CLI、优先已有 seams、保留诊断等不冲突的原则继续有效。执行本规格不应重新实现已经存在的测试基础或扩大其他模块范围。

### 上游核查基线

设计期间本机 Codex 为 0.150.1；对应版本与当时最新主线的 image tool 均明确请求 gpt-image-2，而不是由 wrapper 指定 gpt-image-2.5。这是核查时的事实，不是永久模型锁定。

最新主线已包含透明背景参数，并明确支持最多五张参考图、合法本地查看图片、附件引用与异步等待。实施时重新核对最新适用版本，记录实际验证版本，而不是仅复制本段观察。

### 已确认的取舍

用户明确授权通过 Codex 高级订阅自动重新生成；预算设计用于避免失控和重复任务，不以单次付费 API 成本为前提。艺术接受权仍属于用户。所有有效结果都展示，并清楚解释恢复、重试及异常情况。
